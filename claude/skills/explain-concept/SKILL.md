# /explain-concept

모르는 개념을 **1차 자료 조사 → 지식 구조화 → 디자인 계획 → 작성 → 검산** 순서로 정리한다.
기본 산출물은 자립형 HTML 한 파일. 필요하면 Markdown.

## 사용법

```
/explain-concept <주제>                    # 단일 개념 정리
/explain-concept <A> vs <B>                # 두 개념 비교
/explain-concept <주제> --md               # HTML 대신 Markdown
/explain-concept <주제> --deep             # 1차 자료 5개 이상, 원논문·소스코드까지
/explain-concept <주제> --brief            # 조사 3출처, 한 화면 분량
```

## 핵심 원칙 넷

1. **1차 자료가 먼저다.** 표준 문서·공식 문서·원논문을 읽고, 블로그는 수치와 현장 관행 보강에만 쓴다. 장황한 설명글은 대부분 2차 자료 여러 개를 평균 내다가 핵심 문장을 잃어서 나온다.
2. **Structure is information.** 번호, 연도, 대칭 배치 같은 구조 장치는 내용에 대해 참인 것만 담는다. 번호 마커는 내용이 실제로 순서일 때만 쓴다.
3. **관점으로 조사하고, 구조는 결과에서 도출한다.** 관점 목록은 무엇을 캐낼지 정할 뿐이다. 그것을 그대로 목차로 옮기면 모든 문서가 같은 모양이 된다.
4. **디자인은 코드 전에 문장으로 정한다.** 팔레트·서체·레이아웃을 먼저 적고, 그 계획대로만 코딩한다.

## Phase 0. 스코프 확정

한 번에 답하고 넘어간다. 사용자에게 되묻지 않는다. 다만 아래 네 줄을 작업 시작 전에 스스로 적는다.

| 항목 | 예시 |
|---|---|
| 주제 | RTSP와 HLS |
| 독자 | 관련 배경은 있으나 이 주제는 처음인 사람 |
| 이 문서가 답할 질문 하나 | 왜 둘 다 존재하고 언제 무엇을 고르나 |
| 산출물 | 자립형 HTML 한 파일 |

질문이 하나로 안 좁혀지면 조사 범위가 무한히 늘어난다. 먼저 좁혀라.

## Phase 1. 자료 우선 조사

### 출처 등급

| 등급 | 무엇 | 쓰임 |
|---|---|---|
| 1차 | 표준 문서(RFC/ISO/W3C/IEEE), 공식 문서, 원논문, 사양서, 소스코드 | 정의, 메커니즘, 규칙, 인용문 |
| 2차 | 벤더 문서, 기술 블로그, 위키백과 | 수치, 현장 관행, 연혁 확인 |
| 금지 | 요약 사이트, 출처 없는 글, 다른 AI 출력 | 쓰지 않는다 |

**최소 조건: 1차 자료 1개 이상, 독립 출처 3개 이상.** `--deep`이면 1차 5개 이상.

페치할 문서가 3개 이상이면 **사용자에게 트랙을 묻는다.** 서브에이전트를 자동으로 띄우지 않는다.
질문 방법은 아래 [두 트랙](#두-트랙).

### 관점 은행

조사는 **관점**으로 한다. 아래는 후보 목록이지 목차가 아니다. 주제에 맞는 것을 4~7개 고르고, 조사하면서 답이 안 나오거나 얇은 관점은 버린다. 목록에 없는 관점이 필요하면 추가한다.

| 관점 | 답해야 할 질문 |
|---|---|
| 문제 정의 | 이게 없으면 무엇이 불편한가. 어떤 고통을 없애는가 |
| 배경 동기 | 언제, 누가, 어떤 상황에서 만들었나. 그때 무엇이 막혀 있었나 |
| 작동 원리 | 핵심 메커니즘 한 가지. 왜 그 방식이 문제를 푸는가 |
| 주요 대안 | 같은 문제를 푸는 다른 답. 갈림길에서 무엇을 맞바꾸나 |
| 발전 경로 | 이후 무엇이 바뀌었나. 무엇이 그 변화를 밀었나 |
| 실용적 한계 | 어디서 깨지나. 성립하려고 무엇을 포기했나 |
| 적용 조건 | 언제 쓰고 언제 안 쓰나 |
| 비용 구조 | 무엇이 비싸고 무엇이 싼가. 시간·돈·복잡도·운영 부담 |
| 전제와 가정 | 무엇이 참이어야 성립하나. 그 가정이 깨지면 |
| 오해와 함정 | 사람들이 자주 틀리는 지점 |
| 경계와 인접 개념 | 무엇과 헷갈리나. 어디까지가 이것인가 |
| 증거 상태 | 얼마나 확립됐나. 논쟁 중인 부분은 어디인가 |

**주제 유형별 출발 후보** (그대로 쓰지 말고 조사하며 갈아탄다)

| 주제 유형 | 출발 관점 |
|---|---|
| 프로토콜·표준·기술 | 문제 정의, 배경 동기, 주요 대안, 발전 경로, 적용 조건 |
| 알고리즘·자료구조 | 문제 정의, 작동 원리, 비용 구조, 전제와 가정, 실용적 한계 |
| 연구 개념·이론 | 문제 정의, 전제와 가정, 경계와 인접 개념, 증거 상태 |
| 도구·라이브러리 | 문제 정의, 적용 조건, 비용 구조, 오해와 함정 |
| 현상·사건 | 배경 동기, 발전 경로, 증거 상태, 실용적 한계 |

**규칙 다섯**

1. **문제 정의는 거의 항상 포함한다.** 이걸 못 쓰면 그 개념을 아직 이해하지 못한 것이다. 작동 원리부터 쓰기 시작하면 장황해진다.
2. **관점은 조사 도구다. 문서의 목차가 아니다.** 관점 하나가 섹션 하나로 그대로 옮겨 가는 것이 기본값이 아니다. 구조는 Phase 2에서 조사 결과를 보고 새로 만든다.
3. **버린 관점을 기록한다.** "발전 경로: 자료 없음, 제외" 한 줄. 나중에 빠진 게 실수인지 판단인지 구분된다.
4. **조사 중 예상 못 한 관점이 튀어나오면 채택한다.** 목록은 출발점이지 울타리가 아니다.
5. **관점은 분할 축이 아니다.** 관점으로 조사원을 나누면 같은 논문을 여러 명이 각자 연다. 나누는 단위는
   문서이고, 관점은 조사원 전원이 들고 들어가는 질문지이자 부모가 나중에 채우는 커버리지 체크리스트다.

### 출처 대장

조사하면서 표를 만든다. 문서의 출처 섹션이 여기서 나온다.

```
| 주장 / 수치 / 인용문 | 출처 | 등급 | URL |
|---|---|---|---|
| "network remote control" | RFC 2326 §1 | 1차 | https://... |
| 기본 지연 6~30초 | Wowza 프로토콜 비교 | 2차 | https://... |
```

### 조사 규칙 넷

1. **숫자와 인용문은 출처를 붙인다.** 못 붙일 숫자는 쓰지 않는다.
2. **1차와 2차가 상충하면 1차를 따르고, 상충한다는 사실을 문서에 적는다.**
3. **못 찾은 것은 "확인 안 됨"이라고 적는다.** 그럴듯하게 메우지 않는다.
4. **페치 실패(403/404)는 다른 출처로 대체한다.** 실패한 출처의 내용을 추측으로 채우지 않는다.

## Phase 2. 지식 구조화

구조는 정해진 틀에서 고르는 게 아니라 **조사 결과의 모양에서 도출한다.** 순서는 아래 다섯.

### 1. 작업용 결론

먼저 쓴다. 안 써지면 Phase 1로 돌아간다. 조사가 덜 된 것이다.

**이것은 조사 완료 게이트다. 문서에 싣는 문장이 아니다.** 조사 노트에만 남긴다.
골격이 없는 상태에서 쓸 수 있는 것은 절차 요약("무엇을 한다")뿐이고, 그것을 그대로 첫 화면에 옮기면
목적이 빠진 문서가 된다. 독자가 읽을 첫 화면은 골격이 정해진 뒤 5단계에서 조립한다.

### 2. 구조 브레인스토밍

조사 노트를 놓고 세 가지를 묻는다. 답을 한 줄씩 적는다.

| 물음 | 무엇이 걸리나 |
|---|---|
| 이 주제의 핵심 긴장은 무엇인가 | 문제 대 제약, A 대 B, 이상 대 현실, 옛 방식 대 새 방식 |
| 독자가 넘어야 할 가장 높은 턱은 무엇인가 | 그 턱이 문서에서 가장 큰 자리를 차지해야 한다 |
| 내용에 실제로 있는 관계는 무엇인가 | 순서인가, 인과인가, 대등인가, 포함인가, 트레이드오프인가 |

세 답을 보고 **구조 후보 2~3개를 한 줄씩** 적는다. 하나를 고르고 고른 이유를 한 줄로 적는다.

```
후보 A: 연표 중심. 1998 문제 → 2009 문제 → 후속.   (인과가 시간에 실려 있음)
후보 B: 대칭 비교 중심. 항목별 A/B 대조.            (시간 정보가 사라짐)
채택: A. 두 프로토콜이 11년 차이의 인과로 묶여 있어서 시간축이 곧 논지다.
```

### 3. 골격 카탈로그 (참고)

자주 쓰이는 모양들이다. **고르는 메뉴가 아니라 예시다.** 조사 결과가 여기 없는 모양이면 새로 만든다.

| 내용의 모양 | 자주 맞는 골격 |
|---|---|
| 한 개념의 원리 | 결론 → 문제 → 배경 → 작동 원리 → 대안 → 한계 |
| 두 개념 비교 | 결론 → 각자의 정체 → 탄생 동기 → 상호 보완 → 핵심 수치 → 대조표 → 선택표 |
| 여러 대안 중 선택 | 결론 → 문제 축 → 대안별 트레이드오프 → 상황별 선택표 → 함정 |
| 시간이 논지인 것 | 결론 → 연표(문제/해법 쌍) → 지금의 상태 → 남은 숙제 |
| 절차·워크플로 | 결론 → 준비물 → 번호 단계 → 검증 → 실패 시 대처 |

어느 골격이든 **lede가 처음, 출처가 마지막**이다. 이 둘만 고정이다.

### 4. Structure is information 검산

구조 장치는 내용에 대해 참인 것만 담는다. 장식으로 쓰면 거짓말이 된다.

| 장치 | 쓸 수 있는 조건 |
|---|---|
| 번호(01, 02, 03) | 내용이 실제로 순서이거나 순위일 때만 |
| 연도·타임라인 | 날짜가 인과를 담을 때만. B가 A의 문제 때문에 생겼을 때 |
| 대칭 카드 2장 | 두 항목이 실제로 대등한 선택지일 때만 |
| 크기·굵기 차이 | 중요도 차이가 실제로 존재할 때만 |
| 차트 | 비교할 수치가 실제로 있을 때만. 장식용 차트 금지 |

각 구조 장치 옆에 "이게 왜 참인가"를 한 줄로 적어 본다. 못 쓰면 그 장치를 뺀다.

### 5. lede 조립

lede는 문서 첫 화면에 오는 3~6문장이다. **골격이 확정된 뒤에 쓴다.** 재료는 확정된 섹션 목록이다.

**최상위 고르기.** 섹션마다 그 섹션이 답한 "왜"를 한 줄씩 뽑는다. 각 후보를 지웠다고 가정하고, 이해 불가가
되는 섹션 수를 센다. 가장 많이 무너뜨리는 하나가 최상위이고, 그것이 lede의 뼈대다.

```
후보: 마스크가 텐서에 걸린다      → 지우면 01만 무너짐
후보: 평균을 학습·추론에서 맞춘다  → 지우면 02, 05, 07이 함께 무너짐   ← 최상위
후보: conv는 채널 단위로 떨어뜨린다 → 지우면 04만 무너짐
```

**규칙 둘.** 슬롯이나 문장 순서를 고정하지 않는다. 이 둘만 지킨다.

1. **절차 서술은 첫 문장 하나까지.** "무엇을 한다"는 한 문장에서 끝낸다. 두 번째 문장이 "왜"가 아니면
   lede 실패다. 다시 쓴다.
2. **커버리지 매핑이 뚫려야 한다.** lede 문장마다 어느 섹션을 덮는지 적는다.

```
lede-1 → 01, 02
lede-2 → 02, 05, 07      ← 최상위
lede-3 → 02, 05
lede-4 → 04, 05
미커버 섹션: 03, 06       → 1개 이하면 통과
```

- 어느 섹션에도 안 걸리는 lede 문장은 지엽적이다. 지운다.
- lede 어느 문장에도 안 걸리는 섹션이 2개 이상이면 lede가 전체를 가로지르지 못한 것이다. 다시 쓴다.
- 매핑은 조사 노트에 남긴다. 문서에는 싣지 않는다. 나중에 lede를 고칠 때 근거가 된다.

**두 번 쓴다.** 여기서 초안을 쓰고, 본문을 그 초안에 맞춰 쓴다. Phase 5에서 실제 본문과 대조해 확정한다.
초안과 본문이 갈라졌으면 본문이 옳다. lede를 고친다.

### 배치 규칙 다섯

1. **비대칭을 정보로 쓴다.** 중요한 항목에만 살을 붙인다. 네 칸을 똑같이 채우면 무엇이 중요한지 사라진다.
2. **숫자는 한 곳에 모은다.** 그리고 그 숫자가 나온 원인을 규칙·근거로 못 박는다.
3. **한 섹션 5항목 이하.** 넘으면 지금 할 것과 나중 것으로 쪼갠다.
4. **양방향 비교는 개수와 형식을 맞춘다.** 비대칭이 되는 순간 "무엇이 더 좋은가"라는 무의미한 글이 된다.
5. **시제로 전환을 표시한다.** 문제는 과거형, 해법은 현재형. 헤더를 안 봐도 구간이 바뀐 걸 안다.

## Phase 3. 디자인 계획

코드를 쓰기 전에 아래 네 줄을 문장으로 적는다. 그다음 이 계획대로만 코딩한다.

| 항목 | 정하는 법 |
|---|---|
| 팔레트 | 4~6개, 이름 + hex. **주제의 세계에서 유래를 끌어온다** (영상 프로토콜 → SMPTE 컬러바 + 18% 그레이 카드) |
| 서체 | 역할 2개. 본문·제목용 하나 + 라벨·수치용 모노 하나. 한국어면 한글 지원 확인 |
| 레이아웃 | 한두 문장. 예: 단일 컬럼, 왼쪽 고정폭 라벨 거터, 헤어라인 구분선만 |
| 강조 방식 | 색이 아니라 밝기로. 바탕은 살짝 회색, 강조 블록은 흰색 |

상세 지침과 회피 목록은 `references/design-principles.md`.
복붙 가능한 CSS·HTML 골격은 `references/patterns.md`.

## Phase 4. 작성

문체 규칙. 산출물이 HTML이든 Markdown이든 동일하다.

1. **첫 화면은 lede.** Phase 2의 5단계에서 조립한 것을 그대로 쓴다. 배경 설명으로 시작하지 않는다.
   절차 서술은 첫 문장 하나까지, 두 번째 문장은 최상위 "왜".
2. **헤더는 명사구.** "지연이 생기는 자리"는 되고 "지연은 왜 생기는가"는 안 된다.
3. **부사 삭제, 능동태, em-dash 금지.** 쉼표·콜론·괄호·마침표로 대체.
4. **한 문장 한 생각.** 설명이 필요한 용어는 교체 대상이다.
5. **출처 섹션 필수.** 등급(1차/2차)과 무엇을 가져왔는지 한 줄씩.

## Phase 5. 검산

내보내기 전에 전부 통과해야 한다. 대조는 Phase 1에서 고른 트랙을 그대로 따른다. 여기서 다시 묻지 않는다.
서브에이전트 트랙이면 검증원과 구조 비평가를 띄우고, 인라인 트랙이면 아래
[인라인 트랙](#인라인-트랙-기본값)의 순서대로 직접 대조한다.

- [ ] lede가 첫 화면에 있고, 두 번째 문장이 최상위 "왜"다
- [ ] lede 커버리지 매핑이 조사 노트에 있고, 미커버 섹션이 1개 이하다
- [ ] 본문을 다 쓴 뒤 lede를 실제 본문과 대조해 확정했다
- [ ] 고른 관점마다 답이 있다. 버린 관점은 버린 이유가 조사 노트에 있다
- [ ] 구조 후보를 2개 이상 검토하고 고른 이유를 댈 수 있다
- [ ] 모든 숫자와 인용문에 출처가 붙어 있다
- [ ] 1차 자료 1개 이상 (`--deep`이면 5개 이상)
- [ ] 구조 장치마다 "왜 참인가"를 한 줄로 댈 수 있다
- [ ] 확인 못 한 것은 "확인 안 됨"으로 표시했다
- [ ] 검증원을 띄웠다면 DRIFT와 NOT FOUND가 문서에 남아 있지 않다
- [ ] 한 섹션 5항목 이하
- [ ] HTML이면 라이트·다크 양쪽에서 읽힌다 (색을 미디어쿼리 안에서만 정의하지 않았다)
- [ ] HTML이면 표·코드·다이어그램이 자기 컨테이너 안에서 가로 스크롤된다

## 두 트랙

서브에이전트는 아직 불안정하다. **인라인이 기본값이고, 서브에이전트는 사용자가 고를 때만 쓴다.**

**묻는 시점은 한 번뿐이다. Phase 1의 정찰 직후, 페치 대상이 3개 이상으로 확정된 순간이다.** 그 답이 실행
전체에 적용된다. Phase 5에서는 묻지 않고 같은 트랙을 따른다. 늦게 물으면 고를 것이 없다. 트랙 선택이
실제로 일을 바꾸는 시점은 **전문을 열기 직전** 하나뿐이다.

물을 때 문서 개수와 그중 PDF·논문 수, 서브에이전트로 가면 띄울 조사원 수, 인라인의 대가(부모 컨텍스트를
많이 쓰고 순차라 느리다)를 함께 보여 준다. 판단 재료 없이 물으면 사용자가 고를 수 없다.

- 정찰에서 문서가 2개 이하면 묻지 않는다. 전 구간 인라인이다.
- 답을 받을 수 없는 런타임(백그라운드, 크론, 서브에이전트 미지원)이면 묻지 않고 인라인으로 간다.
- 한 번 고른 트랙은 실행이 끝날 때까지 바뀌지 않는다. 2차 라운드에서 후보가 늘어나도 다시 묻지 않는다.
  규모를 처음 수준으로 유지하는 것은 부모의 몫이다.

**서브에이전트를 고르면 `references/subagents.md`를 읽고 그 순서대로 배정한다.** 넘길 프롬프트는
`agents/researcher.md`, `agents/verifier.md`, `agents/critic.md`에 그대로 쓸 수 있는 형태로 있다.
쪼개면 안 되는 것은 Phase 2 지식 구조화, lede, Phase 4 작성이다.

### 인라인 트랙 (기본값)

순차로 직접 한다. 분업은 비용을 줄이는 장치이지 품질 기준이 아니다. 판정 기준은 트랙과 무관하게 같다.

- 조사: 문서를 하나씩 열되 인용문·출처·등급·URL 네 칸을 그때그때 대장에 채운다. 나중에 몰아 적지 않는다.
- 검산: 수치와 인용문 목록을 먼저 뽑아 놓고, 본문을 보지 않은 채 원문과 하나씩 대조한다. 순서를 뒤집으면
  본문이 정답처럼 보여서 대조가 형식만 남는다.

## 흔한 실패 다섯

| 증상 | 원인 | 고치는 법 |
|---|---|---|
| 장황하고 핵심이 안 보인다 | 2차 자료 여러 개를 평균 냈다 | 1차 자료의 정의 문장 하나를 찾아 그것부터 인용 |
| 비교글이 "무엇이 더 좋은가"로 흐른다 | 양방향 비대칭 | A→B, B→A를 같은 개수·같은 형식으로 |
| 예쁘지만 뭘 말하는지 모르겠다 | 구조 장치가 장식이다 | 구조 검산. 근거 못 대는 장치 제거 |
| 원리는 이해했는데 왜 쓰는지 모르겠다 | 문제 정의를 건너뛰었다 | 문제 → 해법 순서로 다시 배치 |
| 첫 화면이 절차 요약이라 목적이 안 보인다 | 골격 전에 쓴 작업용 결론을 그대로 실었다 | Phase 2의 5단계로 돌아가 최상위 "왜"를 다시 고르고 lede를 조립 |
| 섹션이 관점 목록과 1대1로 똑같다 | 조사 도구를 목차로 그대로 옮겼다 | Phase 2의 구조 브레인스토밍을 실제로 수행 |

## 다른 에이전트에서 쓰기

이 스킬은 특정 도구에 묶이지 않는다. 웹 검색과 파일 쓰기만 있으면 된다.

- **Codex / Gemini CLI / Copilot CLI**: 이 폴더를 `~/.agents/skills/explain-concept/`에 복사하거나, `SKILL.md` + `references/*.md`를 프롬프트에 붙여 넣는다.
- **웹 챗 인터페이스**: 세 파일을 이어 붙여 첫 메시지로 넣고, 다음 줄에 주제를 적는다.
- **도구 이름은 일반어로 쓰여 있다.** "웹 검색", "페치", "파일 쓰기". 각 런타임의 해당 도구로 바꿔 읽으면 된다.
